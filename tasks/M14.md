# Task M14 — the toolsmith stage: the agent builds and verifies its own tools

Spec: `SPEC.md` §2 (Principles 2, 4, 5), §4. Read `physics_proof/agent.py`, `physics_proof/sandbox.py`,
`physics_proof/schema.py` first.

Why: the verified `blocks` library covers what we foresaw. A new clip needs measurements nobody wrote yet (for the
wall run we had to add a wall-attached frame of reference and a gait signal by hand). The agent should be able to build
such a tool itself — but a tool only counts if it passes a probe on synthetic data where the answer is known, exactly
how our own blocks are accepted. Tools that prove useful can later be promoted into the library by a human: the toolbox
grows from clip to clip.

## Build
1. **Agent tool `make_tool(name, code, probe)`**:
   - `name`: snake_case module name; `code`: Python source of the module (functions with docstrings that state argument
     shapes and units); `probe`: Python test code that imports the module, builds synthetic data with a known answer,
     checks the result with explicit tolerances, and prints `PASS` at the end.
   - Both pass the same static review as `python` (M5). The module is written to `workspace/tools/<name>.py`, the probe
     to `workspace/tools/<name>_probe.py`; the probe runs in the sandbox with `workspace/tools` importable.
   - Registered only if the probe exits 0 and prints `PASS`; then later `python` calls can `import <name>` (from
     `workspace/tools`). A failed probe returns its output to Spark; the module stays unregistered. Re-registering the
     same name replaces it (keep every version on disk).
   - Limits: 4 registered tools per run, 3 attempts per name (configurable); each attempt counts as a turn.
   - `workspace/tools/registry.json`: name, purpose (first docstring line), public functions with signatures, probe
     source, probe output, turn, attempt.
2. **Prompt**: a short "Plan, then build what is missing" section: after the first look, write down which measurements
   the clip needs and which `blocks` cover them; for anything missing, build a tool with `make_tool` and a probe on
   synthetic data with a known answer before using it for any number in the analysis.
3. **Schema and finish**: an optional `tools` section in `analysis.json` — `[{name, purpose, functions, probe_summary,
   verified}]` — **filled by `finish` from the registry**, not written by the agent. Document it in `schema_doc()`.
   The page (M10, being built in parallel) will show it later; do not touch `player/`.
4. **Promotion**: `python -m physics_proof promote <run_dir> <tool>` copies the module to
   `physics_proof/contrib/<tool>.py` and turns its probe into `tests/contrib/test_<tool>.py` (a pytest test that runs the
   probe body), with a header comment naming the run it came from. A human reviews and commits.

## Probes (tests, offline, fake Spark)
- A tool with a passing probe is registered and importable in a later `python` call; its registry entry is complete.
- A failing probe (wrong answer) is rejected with its output; the module is not importable.
- A tool importing a banned module is refused by the review, without running anything.
- The per-run tool limit and the per-name attempt limit hold.
- `finish` fills `analysis.tools` from the registry; a run without tools has no `tools` section.
- `promote` creates both files and the generated test passes under pytest.

## Done when

and a real run.
